# Chapter 6: Red Teaming and Jailbreak Evaluation

Chapters 3-5 built and stress-tested a classifier. This chapter turns the target of the experiment into the language model itself: **Qwen/Qwen3-0.6B**, a small, Apache-2.0, post-trained conversational model chosen specifically so the entire red-team loop (generate, attack, evaluate) is visible and runs on ordinary hardware. Red teaming is treated as an experiment, not a search for a clever prompt: a target behaviour, target model, generation configuration, attack condition, evaluator and threat model all have to be recorded for a result to mean anything.

The notebook [`chapter_6_red_teaming_and_jailbreak_evaluation.ipynb`](chapter_6_red_teaming_and_jailbreak_evaluation.ipynb) reproduces the chapter's harness end to end. Running it top to bottom will:

- load JailbreakBench's JBB-Behaviors harmful and benign sets, keeping raw goal text out of routine output (hashes and categories only);
- load Qwen3-0.6B (non-thinking mode) and build one shared generation function used by every condition;
- run a direct-prompt harmful baseline and save the raw completions before any judging happens;
- implement a lexical refusal-rule judge and show why refusal rate is not the same as attack success rate;
- reuse the **BeaverTails TF-IDF classifier from Chapters 3-4** as a second evaluator signal (in place of the book's heavier, gated WildGuard option), explicitly flagged with the same limitation the book describes for this evaluator family: it detects harmful-sounding content, not whether the specific requested behaviour was fulfilled;
- build a stratified sample for manual human audit of the automated judge (the label column is left for you to fill in by hand);
- calculate category-specific attack success rate;
- load a public PAIR transfer-attack artifact from JailbreakBench and run it against the *same* behaviours as the direct baseline, so attack lift and a paired conversion rate are actually measuring the same underlying requests;
- measure benign refusal rate on JailbreakBench's benign set as the over-refusal side of the trade-off;
- run an optional safety-system-message ablation on a small subset;
- compute bootstrap confidence intervals and a paired McNemar's test rather than reporting point estimates as settled;
- compare the refusal-rule judge against the classifier-based judge and report their disagreement rather than picking whichever number looks better; and
- assemble one long-form result table and a core summary, saved under `results/chapter6/`.

## Why this notebook differs from earlier chapters

Chapters 2-5 needed nothing heavier than `scikit-learn`. This chapter needs an actual language model, `transformers`, `torch`, and the `jailbreakbench` package. Two things worth knowing before you run it:

- **It is slow.** A single generation from Qwen3-0.6B took, in testing on Apple Silicon (MPS), anywhere from about 5 seconds to over two minutes depending on how much the model had to say, averaging roughly 70 seconds. The notebook's `N_HARMFUL` / `N_BENIGN` constants default to a small sample (10 and 8 behaviours) so the full run finishes in well under an hour; set them to 100 to reproduce JailbreakBench's full behaviour sets, matching the book's actual research-project design, if you have the time and compute.
- **`jailbreakbench` needs an older `litellm`.** As of this writing, the latest `litellm` release moved a module that `jailbreakbench` imports directly, which breaks `import jailbreakbench` outright. `requirements.txt` pins `litellm==1.44.27` to work around this. If a future `jailbreakbench` release fixes this, the pin can be relaxed.

## Content handling

JailbreakBench's harmful behaviours and the raw text of every model completion are treated as controlled research artifacts, not display data: they live in the parquet files under `results/chapter6/` (gitignored, regenerated by running the notebook), while every printed table in the notebook itself uses only behaviour IDs, categories, and content hashes. This mirrors the book's own guidance in section 6.2 and is why nothing in this notebook's *outputs* reproduces a harmful prompt or response, even though the underlying (public, academic) dataset does contain them.

## Running it

From the repository root:

```bash
pip install -r requirements.txt
jupyter notebook "Chapter 6/chapter_6_red_teaming_and_jailbreak_evaluation.ipynb"
```

No GPU is strictly required, but this chapter benefits far more from one than earlier chapters did; on Apple Silicon, `torch`'s MPS backend is used automatically. A CPU-only machine will run the same notebook correctly, just considerably more slowly.
